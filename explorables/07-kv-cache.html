The KV cache, counted cell by cell

Module 07 · Inference internals ← All explorables

A decoder-only transformer generating token n needs the keys and values of every earlier token. It can either recompute them all — or remember them. That single choice is the difference between a decode loop that stays fast and one that falls off a cliff.

Below, the same 128-token generation runs twice side by side, and every attention cell either side computes is counted exactly. Then: the real throughput curve measured by module 07's Zig engine, and the int8 quantization of a real weight row from the same checkpoint. Press space to play or pause.

1Two decode loops, every cell counted

Each square is one attention score — a dot product between the query at row i and the key at column j. The grid is lower-triangular because attention is causal. On the left the cache is on, so each step paints exactly one new row. On the right the cache is off, so each step repaints the whole triangle; cells are shaded by how many times they have been recomputed.

The cell counter in panel 1 predicts this chart. Per step, cache-off does t(t+1)/2 cells where cache-on does t, so the ratio should be (t+1)/2 — 64.5× at t = 128. The engine measures 62.8×. Every row of the table lands within ~7% of the prediction, which is how you know the counter and the wall clock are describing the same thing.

3int8: 3.9× smaller, same perplexity

Weights are near-Gaussian, so almost all of a row's dynamic range is wasted on f32's enormous exponent. Per-row symmetric int8 (scale = max|row| / 127) snaps every value onto a 255-level grid. Real file sizes: 2,479,104 B → 634,480 B = 3.91×. Perplexity and logit error from the module README's quantization table. Honest caveat carried over from the module: this engine dequantizes at load and runs the identical f32 compute path, so decode speed is unchanged (~490 tok/s either way). The win here is bytes on disk and in RAM, at essentially zero quality cost. Real engines also win speed, but only on large memory-bandwidth-bound models with true int8 kernels.

What to notice

  • Slide context n to 128 and play. The left grid paints one thin row per step and stops growing in cost; the right grid keeps re-darkening the same early cells. Row 0's key is recomputed n times for no reason at all.
  • The two totals are exact closed forms, not estimates: cache-on lands on n(n+1)/2 cells and cache-off on n(n+1)(n+2)/6. At n = 128 that is 8,256 versus 357,760 — a 43× difference over the whole generation.
  • Per step the gap is bigger and keeps widening: (t+1)/2. This is why the speedup in panel 2 is not a constant — it is 8× at t = 16 and 63× at t = 128, and it would keep climbing.
  • Turn off the log axis in panel 2. The cache-on curve becomes a flat line and the cache-off curve vanishes into the floor. Linear-vs-quadratic is not a subtle effect.
  • In panel 3, drag to index 98 — that is the row's largest-magnitude weight (0.097437), so it lands exactly on code ±127 with zero error. Every other weight in the row is quantized relative to it; that is what "per-row scale" buys you, and why max |Δ| stays under 4e-4.
  • The cache is free speed but not free memory. Watch the strip in panel 1: 768 floats per position, 384 KB at 128 tokens for a 620K-parameter model. Scale that to a 70B model with a 128K context and the KV cache, not the weights, becomes the thing that does not fit.
