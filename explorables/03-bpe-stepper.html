BPE, one merge at a time

Module 03 · Tokenization ← All explorables

A byte-level BPE tokenizer is just an ordered list of merges. Start from raw UTF-8 bytes, then repeatedly glue the most frequent adjacent pair into one new token. The 60 merges below are the real first 60 learned by module 03's from-scratch trainer on tiny-shakespeare — the same list its Python and Zig implementations produce byte-for-byte. Press space to play, watch the pairs fuse, and type your own text to see the same merges applied to something the tokenizer never trained on.

The merge list = the model

    What to notice

    • Merge 0 is "e" + " " → "e ", not a word. Byte-level BPE learns trailing spaces first because English is full of words ending in e. Space-prefixed pieces (" th", merge 17) show up soon after — that's why real tokenizers give you " the" rather than "the".
    • Merges compose. Merge 39 glues token 257 ("th") to token 256 ("e ") to make "the ", and merge 48 glues " th"+"e " into " the " — four bytes in one token. Later merges can only fire because earlier ones already ran, so order is the model.
    • Watch bytes/token climb while the byte count never changes. That ratio is the whole economic argument for subwords: fewer positions for the same text means shorter context and cheaper attention. Module 03's compression curve shows the first ~100 merges buy far more than the next 400.
    • Type something un-Shakespearean — a URL, French, emoji, aaaaaaaa. The merges still apply (there is never an unknown token, because the base vocabulary is all 256 bytes), but they buy much less: that gap is exactly the fertility unfairness the module measures across languages. Some merges will report no occurrence — those merges are dead weight for your text.
    • Colours are token length (viridis). Purple chips are single bytes; yellow chips are the 4–7 byte whole-word tokens that only appear once the vocabulary gets big.
