Neural-Symbolic Bridge

concept created 2026-04-13 updated 2026-04-13 neural-symbolic program-synthesis differentiable-logic runtime

The working thesis of this wiki: neural and symbolic are not opposed — they are two parts of the same machine-learning architecture. The interesting question is where the seam lives and how the two substrates articulate. This concept page maps the research actively working on that middle point.

Anchor: source-neural-computer-metauto (Zhuge, 2026) — proposes the Neural Computer as a new machine form that absorbs programs, agents, and world models into a single learned runtime. Its CNC criteria (Turing completeness + universal programmability + behavior-consistent updates + machine-native semantics) define what a mature bridge would look like.

Five axes of articulation

1. Where the verifier lives

When the LLM can propose but not arbitrate. A deterministic symbolic backend checks every candidate.

  • source-funsearch — evolutionary program search, verified execution
  • source-alphaevolve — scaled FunSearch with plug-in evaluators
  • source-logic-lm — LLM parses to logic, Prolog/SAT/FOL solver answers
  • source-satlm — LLM writes SMT spec, Z3 solves
  • source-draft-sketch-prove — LLM drafts, Lean/Isabelle verifies
  • source-pal-program-aided-lm — LLM writes Python, interpreter runs it

2. Where the library lives

The accumulating symbolic artifact — a growing typed DSL where each solved problem contributes a reusable routine. This is the closest existing analogue to the Neural Computer's "installable capabilities."

  • source-dreamcoder — wake-sleep library growth with neural recognition
  • source-lilo-library-learning — LLM-guided synthesis + Stitch compression + AutoDoc
  • source-voyager-minecraft-skill-library — an LLM accumulating a JS skill library through play

3. Where the translation happens

Between a symbolic source language and neural weights. Ideally a round trip.

  • source-weiss-2021-thinking-like-transformers-rasp — RASP as the symbolic target language
  • source-tracr-compiled-transformers — RASP → transformer compiler (forward)
  • source-decompiling-transformers-to-rasp — transformer → RASP decompiler (backward)
  • source-weights-to-code-discrete-transformer — weights → Python program decompilation
  • source-weiss-dfa-extraction — DFAs extracted from RNNs via L*
  • source-subleq-transformer-computer — transformer manually constructed as a universal computer

4. Where the soft bridge lives

Keep symbolic structure (logic programs, rules, proofs) but make the crisp operations differentiable so gradients can flow through them.

  • source-neural-theorem-provers — soft unification via embedding similarity
  • source-deepproblog — ProbLog with neural predicates, end-to-end via WMC compilation
  • source-dnc-graves — differentiable addressable memory

5. Where the handles live

Symbolic-looking atoms that already exist inside dense weights and can be read or written at fact-level granularity.

  • source-rome-memit-factual-editing — facts as rank-one edits in middle-layer MLPs
  • source-sae-scaling-trilogy — Golden Gate Claude: SAE features behave like symbols
  • source-circuit-tracing-methods-anthropic, source-lindsey-2025-biology-of-llm — causally-verifiable symbolic sub-computations
  • source-conditional-activation-steering-cast — conditional rules over the feature substrate

World models as programs

Special case worth its own note: using code itself as the world model the agent reasons over.

  • source-worldcoder — world model is a Python program the LLM edits
  • source-rap-reasoning-planning — LLM-as-world-model + MCTS

Open questions

  1. Is there a CNC-shaped architecture? Zhuge argues current dense transformers can't be the endpoint — we need sparser, addressable, more circuit-like substrates. What would that look like concretely?
  2. Can symbolic extraction scale? Decompilation to RASP/Python works on small or specially-designed transformers. Does it extend to frontier models without architectural cooperation?
  3. Are SAE features really symbols? They behave like handles, but they're still linear directions — lacking composition, types, quantifiers. What's missing to make them a language?
  4. Does the verifier-at-the-edge pattern generalize? Math/code/logic have verifiers. Most domains don't. What's the equivalent for biology, economics, social reasoning?
  5. Where does continual learning fit? Neural Computer calls for "behavior-consistent updates with trackable traces." ROME/MEMIT can edit facts but not skills. The skill-library line (DreamCoder, Voyager) accumulates but doesn't edit.
