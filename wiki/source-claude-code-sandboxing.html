Claude Code Sandboxing

source created 2026-05-06 updated 2026-10-20 developer-tools ai-agents security sandboxing claude-code 2026

Anthropic — Claude Code documentation Raw copy: raw/web-2026-claude-code-sandboxing-docs.md (the page as served on 2026-10-20), cited below as R with its section. The docs change; this page was first written from them on 2026-05-06.

Built-in sandboxing for Claude Code's bash tool. Replaces per-command permission prompts with defined boundaries (filesystem and network), enforced at the OS level via Seatbelt (macOS) or bubblewrap (Linux/WSL2). Inside the sandbox, bash runs without prompting; outside it, attempts are blocked or surfaced as confirmation requests.

Mechanism

  • Filesystem isolation: read access to the whole machine (with deny rules), writes allowed in the working directory, a per-user temp directory and added directories; filesystem.allowWrite / denyWrite adjust it (docs as of 2026-10-19). Enforced at OS level so subprocesses (kubectl, terraform, npm) inherit the boundary. (R, "What the sandbox restricts"; "Filesystem isolation")
  • Network isolation: outbound traffic routed through a proxy; only allowlisted hostnames pass. New domains trigger user confirmation. Hostname-based, not TLS-inspecting — so allowing broad domains like github.com opens domain-fronting paths.
    • Superseded (2026-10-20): a new domain prompts only in manual and acceptEdits modes; auto mode refuses it unless the command named the host and the classifier approved, dontAsk refuses it, bypassPermissions allows it (R, "Hosts outside your allowed domains"). An experimental network.tlsTerminate setting now lets the proxy terminate TLS, for credential masking only, with no content filtering (R, "Security limitations").
  • Open-source runtime: published as @anthropic-ai/sandbox-runtime on npm (R, "OS-level enforcement").
  • Escape hatch: dangerouslyDisableSandbox parameter routes through normal permission flow when sandboxed execution fails (configurable via allowUnsandboxedCommands: false) (R, "The unsandboxed retry escape hatch").

Why It's Wiki-Relevant

  • Directly addresses prompt-injection blast radius: a compromised agent inside the sandbox cannot exfiltrate SSH keys or modify ~/.bashrc.
    • Contradiction (partial), 2026-10-20: by default sandboxed commands can read "credential files such as ~/.ssh and ~/.aws/credentials", and inherit secrets in the environment; only the network allowlist stands between them and exfiltration, and a broad allowed domain can undo it. Blocking needs sandbox.credentials or filesystem.denyRead; there is "no built-in credential deny list" (R, "What the sandbox restricts"; "Protect credentials"; "Scope"). The docs call the sandbox "not a complete isolation boundary" (R, "Limitations").
  • Concrete instance of harness-as-substrate: the sandbox is part of the symbolic infrastructure that constrains what the fuzzy LLM can do — see concept-harness-as-symbolic-substrate.
  • Notable design choice: sandbox + permissions are complementary layers, not redundant. Permissions gate which tools run; sandboxing gates what those tools can touch. Defence-in-depth over defence-in-prompt.
  • Documents Auto-allow vs. Regular-permissions modes — design space for autonomy/safety trade-offs (R, "Sandbox modes").

Added 2026-10-20, from R

  • Off by default; /sandbox or sandbox.enabled turns it on (R, "What the sandbox restricts").
  • Protected paths. Inside writable directories, writes stay denied to the files Claude Code loads configuration and code from (.claude settings, skills, hooks, .mcp.json), to shell startup files and .gitconfig in the working directory, and to most of ~/.claude; no setting exempts one path (R, "Protected paths").
  • Credential masking. A masked secret shows sandboxed commands a placeholder; the proxy puts the real value back only on requests to allowed hosts, which needs TLS termination at the proxy (R, "Mask credentials").
  • Local addresses. An allowed hostname that resolves only to loopback, link-local (such as the cloud metadata address 169.254.169.254) or the machine's own addresses is refused (R, "Hostnames that resolve to local addresses").
  • Per-command hosts in auto mode. A command can name the hosts it needs; a classifier reviews them with the command, and they open for that command alone (R, "Per-command allowed domains in auto mode").
  • More limits: a weaker nested mode for Docker on Linux "considerably weakens security"; allowAppleEvents on macOS lets sandboxed commands launch apps unsandboxed (R, "Security limitations").

Limitations Noted

  • TLS not inspected — broad allowlists are exploitable (R, "Security limitations").
  • Unix socket allowlists can grant accidental privilege escalation (e.g. /var/run/docker.sock) (R, "Security limitations").
  • Runs on macOS, Linux and WSL2. On native Windows, commands run unsandboxed; use WSL2 (docs as of 2026-10-19; R, opening).
  • The sandbox covers shell commands only (Bash, PowerShell, Monitor). Claude's file tools, MCP servers and hooks run outside it. excludedCommands run with full access. allowUnsandboxedCommands: false plus failIfUnavailable gives a strict mode (docs as of 2026-10-19; R, "What runs outside the sandbox", "Turn off the retry with strict sandbox mode").
