BeNice!: one KV cache for every loop of a looped model

source created 2026-10-23 updated 2026-10-23 looped-transformers recurrence kv-cache inference memory fixed-point stochastic-depth 2026

Authors: Hayden Prairie, Jacob M. Ryan, Taylor Berg-Kirkpatrick, Daniel Y. Fu (UC San Diego; Together AI) Published: arXiv 2610.31633, v1 2026-10-22 Raw copy: raw/arxiv-2610-31633-benice-closing-looping-s-inference-memory.md (full text of v1 from the arXiv HTML; cited as R, with its section)

Terms

  • Looped model. A transformer that runs the same middle block T times before the final layers ("prelude, recurrent block, coda"), so depth grows without more parameters (R, §2.1).
  • KV cache. During generation, attention keeps the keys and values of every earlier token for every layer, so it need not recompute them. Its memory grows with context length times depth; in a looped model each loop adds its own cache, so memory grows linearly with T (R, §2.2).
  • KV-sharing. Keep only the last loop's cache and let every loop read it. A model is KV-shareable if quality survives this (R, §1).
  • Stochastic depth (here). Training with a different number of loops T for each sequence, drawn from a Poisson distribution (R, §2.1, §4.1).
  • Fixed point / contraction. A contraction is a map that brings any two states closer together, so repeated passes through it settle at one fixed point, a state the next pass leaves unchanged. If the loop's block behaves like one, the hidden state settles, and so do the keys and values computed from it (R, §3.1).

The claim, plainly

A looped model can keep one KV cache instead of one per loop if its loops settle to the same state with or without sharing. Training with a random number of loops makes the state settle, as measured by step-to-step change shrinking across loops (R, §3.1, Figure 2, Appendix F); the authors argue this reflects a contraction, which they do not prove for the trained models, and a short post-training step, BeNice!, fixes the one place where sharing still shifts the result, the first loop's first layer; together they keep quality while sharing (R, Abstract, §3, §4).

Key results

  • Shareability is not automatic. Across released looped models, sharing the final cache costs little for Parcae 140M and 370M and Huginn 3.5B, but much for Parcae 770M and 1.3B and for Ouro 1.4B and 2.6B; Ouro's Core score falls from 54.57 to 25.17 at 1.4B (R, §2.2, Table 1). These shared evaluations share the cache in prefill too, prompt tokens included (R, Appendix C).
  • Random depth makes the state settle. In Parcae models trained from scratch at four sizes, random-depth training gives a validation-perplexity gap between shared and unshared of −0.02 to 0.02; fixed-depth training gives 1.31 to 3.10 (R, §3.1, Table 2). The authors' explanation: tied weights must give good predictions at many depths, which discourages successive states from drifting apart (R, §3.1, footnote).
  • Why it works, on paper. If the block is a contraction, the keys and values converge too, and swapping a loop's cache for the final one changes attention's output by at most an amount tied to how far that loop's state is from the fixed point (R, §3.1, Appendix D).
  • Why it still fails. In Parcae 770M and 1.3B, sharing moves the final state to a different fixed point: up to 177.5% relative difference, against at most 1.69% in shareable models (R, §3.2). The error sits in the first layer of the first loop and is almost the same shift for every token (projected cosine similarity 0.99); adding back the mean shift by hand restores quality (R, §3.2, Table 3).
  • BeNice! post-training. Add a loss term in which the first loop reads the final loop's cache, next to the ordinary loss (R, §4.2). Shared Core then stays within 0.4 points of unshared at all four sizes, where plain Parcae lost up to 5.58 (R, §5.1, Table 4). Against plain fine-tuning on public Parcae checkpoints, shared validation perplexity is 11.86 against 21.61 at 770M (R, §5.1, Table 5).
  • It stacks with other savings. It works with multi-latent attention and Kimi delta attention (other memory-saving attention variants) and with fp8 and 4-bit KV quantisation, changing Core by −0.02 points on average under quantisation (R, §5.2, Figures 6–7).
  • Memory, on a real model. For the trained Parcae 1.3B served in SGLang at batch 64 and context 2,048, GPU memory falls from 63.82 GB to 21.60 GB (R, §5.3).
  • Throughput and latency, on proxy models. In simulated traffic replay, at 2 requests per second throughput rises 23.6% and p90 time-to-first-token falls from 139.2 s to 23.2 s; at 0.5 requests per second there is no gain (R, §5.3). These workload tests use proxy models, built by looping the middle third of GLM 4.7, not trained looped models (R, §5.3).

Caveats

  • Models are small (140M to 1.3B Parcae), plus released checkpoints; BeNice! is tested on Parcae only.
  • The throughput and latency gains come from proxy models and replayed traces, and appear only near saturation (R, §5.3); the memory figure is from the trained Parcae 1.3B.
  • The authors draw a design lesson, that looped models "should favor stochastic fixed-point training over ACT objectives" (learned halting, as in Ouro), from this comparison (R, §3.1). Ouro also differs in architecture: it loops the whole model rather than a middle block (R, Appendix B), so learned halting is not the only difference.
