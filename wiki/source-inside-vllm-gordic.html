Summary

A tour of how vLLM, an open-source LLM inference server, turns prompts into tokens at high throughput. It starts with one GPU running offline and synchronous, then adds features, then many GPUs, then a web server, then measurement (R, intro). The spine is one loop: each engine step() schedules requests, runs one forward pass, samples, and cleans up (R, §"Generate function").

Key claims

  • Prefill vs decode. Prefill runs all prompt tokens at once and is usually compute-bound. Decode runs one new token per request and is memory-bandwidth-bound: all weights (and KV caches) must be read to make one token (R, §"Scheduler").
  • Paged KV cache. The cache is split into blocks of 16 tokens by default, held in a pool of free blocks, often hundreds of thousands. A table maps each request to its blocks, so a request's cache need not sit in one contiguous piece of memory (R, §"LLM Engine constructor"; §"Scheduler", allocate_slots). Bytes per block for a standard (non-MLA) layer: 2 × block_size × num_kv_heads × head_size × dtype bytes (R, §"LLM Engine constructor").
  • Sizing the cache. At start-up the engine runs a dummy forward pass, measures free GPU memory, and fills it with as many KV blocks as fit (R, §"LLM Engine constructor", "Initialize KV cache").
  • Continuous batching. All sequences in a step are flattened into one long sequence; positions and masks keep each sequence attending only to itself, so no padding is needed. New requests can join after any step (R, §"Generate function"; §"Run forward pass").
  • Scheduling. Decode requests go first, then waiting prefills, within a token budget. If blocks run out, the engine can evict low-priority requests and recompute them later (R, §"Scheduler").
  • CUDA graphs. Unless eager mode is forced, the engine records the GPU work for a set of batch sizes at start-up and replays it, which cuts kernel-launch overhead (R, §"LLM Engine constructor"; §"Run forward pass").
  • Chunked prefill. A long prompt is split across steps by capping new tokens per step, so it cannot hold up other requests (R, §"Chunked prefill").
  • Prefix caching. Each full 16-token block is hashed together with the previous block's hash; a later request with the same prefix reuses those blocks. It speeds prefill, not decode, and is on by default (R, §"Prefix Caching").
  • Guided decoding. A grammar, compiled to a finite-state machine by a third-party backend such as xgrammar, gives a bitmask per step; disallowed tokens get logit −∞ (R, §"Guided Decoding (FSM)").
  • Speculative decoding. A cheap proposer guesses k tokens; the large model checks all of them in one pass; an accept/reject rule keeps the output distributed exactly as if the large model had sampled alone (R, §"Speculative Decoding"). At that commit V1 offered n-gram, EAGLE and Medusa proposers, not a separate draft LLM (same section).
  • Disaggregated prefill/decode. Separate prefill and decode instances, joined by a KV transfer "connector", because the two phases have different bottlenecks (R, §"Disaggregated P/D").
  • Scaling. Tensor parallelism inside a node, pipeline parallelism across nodes; data parallel replicas behind a coordinator and an API server; the load balancer scores an engine as 4 × waiting + running (R, §"From UniprocExecutor to MultiProcExecutor"; §"Distributed system serving vLLM"; §"On the API server node").
  • Latency vs throughput. Metrics: TTFT, ITL, TPOT, end-to-end latency, throughput, goodput. Below a saturation batch size a decode step is bound by memory bandwidth and costs about the same for 1 or 10 tokens; above it, step time grows with batch size. So larger batches raise throughput and inter-token latency together (R, §"Benchmarks and auto-tuning - latency vs throughput").

Relevance

Link to the course. course/modules/07-inference-internals builds a KV cache and int8 weights by hand on a 620K-parameter model. It covers the idea under all of this post: decode reuses cached keys and values, so a step costs O(context) instead of O(context²) (course/modules/07-inference-internals/README.md, "The KV cache lab").

The course also states that int8 speeds decode only on large, memory-bandwidth-bound models (same README, "The quantization lab"). The post supports the premise: decode is bandwidth-bound below a saturation batch (R, §"Scheduler"; §"Benchmarks and auto-tuning"). Inference by the wiki, not in the post: above that batch size the saving in weight bytes should matter less.
