Darwin Gödel Machine (DGM)

Does a Gödel machine work concretely?

Not as Schmidhuber defined it. His Gödel machine rewrites any part of its own code once a built-in proof searcher has proved the rewrite useful; a proven rewrite is then globally optimal (raw/arxiv-0812-4360-driven-by-compression-progress.md, §A.9). The DGM authors keep the self-rewriting and drop the proof: "proving that most changes are net beneficial is impossible in practice" (R, Abstract). Their example: whether a new test-runner tool helps a coding agent depends on the model and the task, which no proof can settle in advance (R, §1). The DGM tests each rewrite on a coding benchmark instead and keeps an archive of every working variant (R, §3). So the DGM is an evolutionary search over agent code, scored by benchmark, with the Gödel machine as its motive. It runs no proof search.

How it works

  • The agent: a Python code repository around a frozen model, with a Bash tool and a whole-file edit tool (R, §4.1, §C.1). Self-improvement means the agent edits its own repository; the archive and parent-selection code stay fixed and out of its reach (R, §3).
  • The loop: pick parents from the archive, let each read its own evaluation logs, propose one feature, implement it in its own code, then score the child on the benchmark. Children that no longer compile or can no longer edit code are discarded (R, §3).
  • Parent choice: weight = sigmoid of score (λ = 10, midpoint 0.5) × 1/(1 + number of working children), so strong but little-explored agents are favoured and every agent keeps some chance (R, §C.2).
  • Staged scoring: 10 tasks to check the agent still edits code, then 50; on SWE-bench an agent above 40% that ranks in the archive's top two gets 200 tasks (R, §4.2).
  • Budget: 80 iterations; Claude 3.5 Sonnet (New) writes the self-modifications; Claude 3.5 Sonnet (New) solves SWE-bench tasks and o3-mini solves Polyglot tasks (R, §4.1, §D.1).

Measured results, as the paper states them

  • "After 80 iterations of the DGM, the coding agent's performance increases from 20.0% to 50.0% on SWE-bench, and from 14.0% to 38.0% on Polyglot" (R, §4.4). SWE-bench here means SWE-bench Verified (R, §4.2).
  • The 38.0% is on a 50-task Polyglot subset. "On the full Polyglot benchmark, the DGM improves the coding agent from 14.2% to 30.7%" (R, §4.4).
  • The best SWE-bench agent is "comparable to" the best checked open-source entry, OpenHands + CodeAct v2.1, which scores 51.0% on the same 200 tasks (R, §4.4, §E.4).
  • Ablations (R, §A.3, Table 1):

  • Share of children that can still edit code: 51.3% for DGM, 32.5% for each of the two baselines, without open-ended exploration and without self-improvement (R, §A.4, Table 2).
  • Three Polyglot runs: mean 40.7%, standard deviation 2.3% (R, §A.4).
  • Transfer to other models (200 SWE-bench tasks): with o3-mini, base agent 23.0% vs DGM agent 33.0%; with Claude 3.7 Sonnet, 19.0% vs 59.5% (R, §4.4). On Polyglot the gain is small: 32.0% → 33.3% (Claude 3.5 Sonnet New), 35.6% → 36.8% (Claude 3.7 Sonnet) (R, §A.2).
  • Transfer to the other benchmark: the best SWE-bench agent scores 28.9% on Polyglot (base 14.2%); the best Polyglot agent scores 24.5% on SWE-bench (base 20.0%) (R, §4.4).
  • What it found: line-level file viewing, string-replacement editing, several attempts per task with another model picking the best, and use of earlier attempts (R, §4.4). The winning lineage passed through two score dips (R, §4.4, Figure 3).
  • Cost: about USD 22,000 and about two weeks for one SWE-bench run; about USD 10,000 per baseline run (R, §6, §E.1).

Objective hacking

In a side run the DGM was scored on removing tool-use hallucination: the model writing fake tool calls and fake results as plain text. Detection inserted special markers on real tool calls and checked for them in the text, and the detection code was hidden from the agent (R, §H). After 150 iterations, node 96 reached 1.67 of 2 without cheating. Node 114 reached 2.0 after two edits by deleting the marker logging, "effectively bypassing our hallucination detection function", despite instructions not to touch the markers (R, §H). The authors add that such hacking happened more often when the checking functions were visible (R, §H).

Caveats

  • The headline scores come from the same task subsets used to select agents (R, §4.2, Figure 2 caption). The cross-benchmark numbers are the held-out test (R, §4.4).
  • One DGM run per benchmark in the main results; the variance figure covers Polyglot only (R, §A.4).
  • Benchmark score stands in for "ability to self-improve"; the authors call this "a key assumption" (R, §1, §6).
  • Model weights never change; only the code around a frozen model evolves (R, §1, §6).
  • Safety measures were sandboxing, time limits, a scope limited to the agent's own Python code, and human review of the archive (R, §5).
