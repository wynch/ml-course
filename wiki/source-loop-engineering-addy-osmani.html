Loop Engineering (Addy Osmani)

source created 2026-07-04 updated 2026-07-04 ai-agents coding-agents developer-tools agent-harness orchestration

Source: Addy Osmani (@addyosmani), X Article "Loop Engineering." Date: 2026-06-08

Summary

Loop engineering is the practice of replacing yourself as the person who prompts the agent — instead you design the autonomous system that prompts it. Osmani frames it as the layer above the agent harness: where harness engineering builds the environment a single agent runs inside, a loop runs that harness on a timer, spawns helper agents, checks their work, records state, and decides what to do next — with no human in the per-turn loop. He quotes Peter Steinberger (@steipete, "you should be designing loops that prompt your agents") and Boris Cherny (@bcherny, head of Claude Code at Anthropic, "I don't prompt Claude anymore… my job is to write loops").

The central observation is that loops used to be bespoke bash you maintained forever, but the pieces now ship inside the products — and the same five primitives appear in both Codex and Claude Code, so the loop design is tool-portable. Osmani is explicitly skeptical: token costs vary wildly, slop and quality drift are real, and the loop "changes the work, it does not delete you from it."

Key Ideas

  • Five primitives + memory. A loop needs: (1) Automations — the scheduled heartbeat that does discovery/triage (/loop, cron, hooks, GitHub Actions; Codex Automations tab + Triage inbox); (2) Worktrees — git-worktree isolation so parallel agents don't collide (Claude Code --worktree flag, isolation: worktree subagent setting); (3) Skills — a SKILL.md folder that writes project intent down on the outside so the agent stops re-deriving it every session; (4) Plugins & connectors — MCP-based access to issue trackers, DBs, Slack, staging APIs, so the loop acts instead of just advising; (5) Sub-agents — separating the maker from the checker. Plus the sixth thing: memory on disk (a markdown file or Linear board) because "the agent forgets, the repo doesn't."
  • The /goal primitive as maker/checker at the stop condition. /loop re-runs on a cadence; /goal runs until a verifiable condition holds, and a separate small model grades doneness after each turn — the agent that wrote the code isn't the one deciding it's finished. Present in both Codex and Claude Code.
  • Tool-portability is the point. Steinberger's list "maps almost exactly onto the Codex app, and then almost the same onto Claude Code" — so you design a loop that works regardless of which tool you're in.
  • The three problems that get sharper, not easier. (a) Verification stays on you — an unattended loop is one making mistakes unattended; "done" is a claim, not a proof. (b) Comprehension debt — the faster the loop ships code you didn't write, the wider the gap between what exists and what you understand. (c) Cognitive surrender — taking whatever the loop returns without an opinion. "Designing the loop is the cure when you do it with judgement and the accelerant when you do it to avoid thinking, same action, opposite result."
  • The leverage point moved, the work didn't get easier. Loop design is harder than prompt engineering, not easier: two people building the identical loop get opposite results depending on whether they use it to move faster on work they understand or to avoid understanding it. "Build the loop. Stay the engineer."
