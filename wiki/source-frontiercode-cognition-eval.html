FrontierCode (Cognition)

source created 2026-07-04 updated 2026-07-04 coding-agents evaluation benchmarks developer-tools code-quality

Source: Cognition (@cognition) on X Date: 2026-06-08

Summary

FrontierCode is a coding evaluation from Cognition (makers of Devin) that deliberately targets what SWE-bench-style benchmarks miss: code maintainability, not just whether tests pass. Each task was authored by leading open-source maintainers and took 40+ hours of work. The framing question is not "does it run?" but "would you actually merge this code?" — the eval scores whether a model's output is code a human maintainer would accept into their project.

The headline signal is difficulty: on the "FrontierCode Diamond" split, the best model (Claude Opus 4.8) scores only 13.4%, with every other frontier model in single digits. This is a wide-open headroom eval, in sharp contrast to concept-swe-bench where frontier models now exceed 70%.

Key Ideas

  • Maintainability as the target metric. "Models write sloppy code that works but isn't maintainable." FrontierCode claims to be the first eval to measure mergeability / would-a-maintainer-accept-this, moving past pass/fail on tests.
  • Expert-authored, high-cost tasks. 40+ hours per task by top open-source maintainers — closer to the DIY-hard-benchmark tradition (GPQA-style "Diamond" tier) than to automatically scraped GitHub issues.
  • Far from saturated. Diamond-split scores (transcribed from the announcement chart):
    • Claude Opus 4.8 — 13.4%
    • GPT-5.5 — 6.3
    • Claude Opus 4.7 — 5.2
    • Gemini 3.1 Pro — 4.7 · GPT-5.4-mini — 4.6
    • Kimi K2.6 — 3.8 · Claude Sonnet 4.6 — 3.5
    • SWE-1.6 — 2.5 · MiniMax M2.7 — 2.4 · MiniMax M2.5 — 1.1 · Kimi K2.5 — 1.0 · Gemini 3.1 Flash Lite — 0.7
  • A quality axis, not just a capability axis. Where SWE-bench asks "can the agent resolve the issue?", FrontierCode asks "is the resolution good enough to merge?" — a distinct dimension as agents move from demo to production codebases.
