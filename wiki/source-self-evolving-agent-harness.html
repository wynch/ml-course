Self-evolving agent harnesses: a taxonomy and a rule for accepting edits

source created 2026-10-23 updated 2026-10-23 harness self-improvement agents evaluation statistics survey 2026

Authors: Chuyang Wei, Haoxiang Guan, Minghang Zhu, Kexin Zhou, Jiyan He, Xiren Zhou, Huanhuan Chen, Yifei Shen (Zhongguancun Academy, University of Science and Technology of China) Published: arXiv 2610.18813, v1 2026-10-13. A longer 66-page version and code are on GitHub (not captured). Raw copy: raw/arxiv-2610-18813-self-evolving-agent-harness.md (full text of the 18-page v1, extracted from the PDF because the arXiv HTML stops partway; cited as R, with its section)

This is a survey and position paper with a short theory section. It runs no new experiments; its tables restate numbers from other papers (R, §3.2, §3.3).

Terms

  • Harness. Everything around a fixed model that governs how it runs: the agent loop, tool dispatch, prompt and context building, memory, context compaction, scheduling of sub-agents, sandboxing and logs (R, §2, Table 1).
  • Harness self-evolution. Using feedback from the agent's own runs to revise the harness, keeping accepted revisions for later runs and keeping the ability to revise again; the model's weights stay fixed (R, §2). The final scoring J must stay outside what the agent can edit (R, §2).

The claim, plainly

Systems that rewrite their own scaffolding can be sorted by what they edit (instructions and memory, tool code, the control loop, or plugin wiring), and an edit should be kept only if it beats the current harness on fresh validation tasks by more than a margin that shrinks with the number of tasks and grows with the number of comparisons made (R, Abstract, §3, §4.2).

Key points

  • What gets edited. Interpreted state (prompts, stored experience, task routing over fixed operators) versus executable revisions: tool and code patches, repository-level control logic, and plugin composition (R, §3).
  • Search is evolutionary. Proposal, assessment and selection map onto evolutionary algorithms: local elitism, archives that keep alternative lineages, and Pareto selection across objectives. All select on measured fitness, so accepted edits can overfit or forget (R, §4.1).
  • Three bounds, under stated assumptions (independent tasks, fixed model and evaluator, loss in [0, 1]) (R, §4.2):
    • expected generalisation gap bounded by the update's sensitivity to swapping one task (stability), for the expected gap, not any single run;
    • forgetting of earlier task distributions bounded by the sum of per-round regression budgets, which are assumptions, not consequences;
    • an admission rule: fix at most K candidates first, then draw m fresh tasks from the uniform mix of past task distributions; accept a candidate only if its measured loss minus the incumbent's loss, plus √(2 ln(KT/δ)/m), is below zero, where K is candidates per round, T rounds, and 1 − δ the confidence (a Hoeffding bound with a union bound). The guarantee covers only that past-task mix, "not arbitrary future distributions" (R, §4.2, Eq. 7–8).
  • The fine print. Reusing validation tasks during search breaks the independence these bounds need, even with secrecy or comparison-count corrections; fresh samples or adaptive-data methods are required (R, §4.2). If the evaluator can differ from the true goal by up to η, the margin grows by 2η (R, §4.2, Eq. 9).
  • Risks. Persistent edits can spread errors across users and teams; rollback cannot undo physical or institutional harm, so emergency stops, privileges and final assessment should stay outside the editable surface (R, §5, §6.5).

Caveats

  • No experiments of its own; the SpreadsheetBench and plugin tables restate other papers, and the authors note those do not show gains at matched cost (R, §3.2, §3.3).
  • The bounds rest on assumptions (independent tasks, fixed evaluator) that many real systems do not meet, as the paper says.
